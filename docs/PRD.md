# სართულების განაწილება მენეჯერებზე — რეპორტი

## Problem
Bitrix24-ის 82 ლისტში («მენეჯერი») ინახება, რომელი თანამშრომელი რომელი პროექტის რომელ სართულებზეა პასუხისმგებელი (96 ჩანაწერი, 40 პროექტი, 17 მენეჯერი). ლისტის სტანდარტული ხედი სტრიქონობრივია: ერთი პროექტის სრული სურათის ან კონკრეტული სართულის პასუხისმგებლის სანახავად რამდენიმე ჩანაწერის გადახედვა სჭირდება. გადაფარვები (ერთი სართული ორ მენეჯერზე) შეუმჩნეველი რჩება. საჭიროა ერთი მატრიცული ხედი, რომელიც ბმულით იხსნება და ყოველთვის მიმდინარე მონაცემებს აჩვენებს.

## Users / roles
| როლი | რას აკეთებს | სიხშირე |
|---|---|---|
| გაყიდვების მენეჯერი | პოულობს, ვინ არის პასუხისმგებელი კონკრეტულ პროექტზე/სართულზე; ამოწმებს საკუთარ სართულებს | ყოველდღე |
| ქოლ-ცენტრი | კლიენტის ზარზე სწრაფად ადგენს, ვის გადაამისამართოს (პროექტი + სართული → მენეჯერი) | ყოველდღე, ზარის დროს |
| ხელმძღვანელობა | ხედავს დატვირთვას მენეჯერებზე (სართულების ჯამი), აღმოაჩენს გადაფარვებს/ხარვეზებს, ექსპორტს Excel-ში | კვირაში / საჭიროებისას |

სულ ≈20 მომხმარებელი. ყველა CRM-ის თანამშრომელია; გვერდზე ავტორიზაცია ამ ეტაპზე არ არის (ბმულით ღია).

## User stories
- **US-1** როგორც ქოლ-ცენტრის ოპერატორი, მინდა ჩავწერო პროექტი და სართული, რომ მაშინვე ვნახო პასუხისმგებელი მენეჯერი და მისი კონტაქტი.
- **US-2** როგორც გაყიდვების მენეჯერი, მინდა ვნახო ერთ ეკრანზე ყველა პროექტი × ყველა მენეჯერი სართულების დიაპაზონებით, რომ სწრაფად გავერკვიო განაწილებაში.
- **US-3** როგორც გაყიდვების მენეჯერი, მინდა გავფილტრო მხოლოდ ჩემი (ან არჩეული) მენეჯერების სვეტები, რომ ზედმეტი ინფორმაცია არ მაწუხებდეს.
- **US-4** როგორც ხელმძღვანელი, მინდა ვნახო ყოველი მენეჯერის სართულების ჯამი, რომ დატვირთვა შევადარო.
- **US-5** როგორც ხელმძღვანელი, მინდა გადაფარვები (ერთი სართული ორ მენეჯერზე) თვალსაჩინოდ იყოს მონიშნული, რომ ლისტში შეცდომა გავასწორო.
- **US-6** როგორც ხელმძღვანელი, მინდა ცხრილი Excel-ში გადმოვწერო, რომ შეხვედრაზე/წერილში გამოვიყენო.
- **US-7** როგორც ნებისმიერი მომხმარებელი, მინდა რეპორტი ყოველ გახსნაზე მიმდინარე მონაცემებს აჩვენებდეს, რომ ლისტში ცვლილების შემდეგ ხელით არაფერი მომიწიოს.

## In scope
- მატრიცა: სვეტები = მენეჯერები (სახელი, Email, ნომერი, შიდა ნომერი), რიგები = პროექტები ანბანურად, უჯრა = სართულების დიაპაზონები + რაოდენობა.
- ფილტრები: პროექტები (multi-select), მენეჯერები (multi-select), სართულით ძებნა პასუხის ხაზით.
- გადაფარვის (კონფლიქტის) მონიშვნა უჯრასა და პროექტის სახელზე, დეტალები tooltip-ში.
- მენეჯერის სვეტში სართულების ჯამი ხილულ პროექტებზე.
- Excel export ხილული ცხრილიდან.
- ცოცხალი წაკითხვა Bitrix24-იდან ყოველ გახსნაზე და «განახლება» ღილაკით.
- ლოკალური გახსნა (`config.js`) და Vercel ჰოსტინგი (proxy, webhook სერვერზე).
- ბეჭდვის ხედი.

## Out of scope
- სართულების განაწილების **რედაქტირება** რეპორტიდან (ჩაწერა 82 ლისტში). რეპორტი მხოლოდ კითხულობს.
- სხვა ლისტების/რეპორტების დამატება ამავე პროექტში.
- ავტორიზაცია / წვდომის შეზღუდვა Vercel-ის გვერდზე (გადაწყვეტილება: ჯერ ღია).
- Cache, ფონური განახლება, ისტორია/აუდიტი (ცოცხალი წაკითხვა საკმარისია).
- ბინის/ერთეულის დონის რუკა.
- Bitrix24-ში ჩაშენებული აპლიკაცია (iframe app).

## Acceptance criteria
- **AC-1** (US-2) Given ლისტში არსებობს ჩანაწერები პროექტისთვის P და მენეჯერისთვის M სართულებით {1..5} და {21..26}, When გვერდი იტვირთება, Then P×M უჯრაში ჩანს `1 - 5, 21 - 26` და `11 სართ.`.
- **AC-2** (US-2) Given ლისტში 96 ჩანაწერია 40 პროექტზე და 17 მენეჯერზე, When გვერდი იტვირთება, Then ცხრილში 40 რიგი და 17 სვეტია, სათაურში ჩანს `40 პროექტი · 17 მენეჯერი · 96 ჩანაწერი`.
- **AC-3** (US-2) Given მენეჯერს user.get-ში აქვს `EMAIL`, `WORK_PHONE`/`PERSONAL_MOBILE`, `UF_PHONE_INNER`, When სვეტის სათაური ჩანს, Then ჩანს სახელი, Email, ნომერი `+995`-ის გარეშე და შიდა ნომერი; ცარიელი ველი ცარიელ ხაზად/«—» რჩება.
- **AC-4** (US-3) Given მომხმარებელი ირჩევს 2 პროექტს და 1 მენეჯერს, When ფილტრი გამოიყენება, Then ჩანს მხოლოდ 2 რიგი და 1 სვეტი; «გასუფთავება» აბრუნებს სრულ ცხრილს.
- **AC-5** (US-1) Given არჩეულია პროექტი «არქი ახმეტელი A», When სართულის ველში იწერება `12`, Then მოინიშნება მხოლოდ ის უჯრა, სადაც 12 შედის, დანარჩენი მქრქალდება, და ზემოთ ჩანს `სართული 12 → არქი ახმეტელი A: <მენეჯერი>`.
- **AC-6** (US-5) Given პროექტში ერთ სართულზე ორი მენეჯერია (მაგ. ქობულეთი რეზორტი C, სართული 10), When ცხრილი ჩანს, Then ორივე უჯრას აქვს წითელი ჩარჩო და `!` ბეჯი, პროექტის სახელთან წითელი წერტილია, tooltip-ში წერია სართული და მეორე მენეჯერი.
- **AC-7** (US-4) Given ხილულია N პროექტი, When ვხედავთ ბოლო ხაზს, Then მენეჯერის ქვეშ წერია მისი სართულების ჯამი მხოლოდ ხილულ პროექტებზე და პროექტების რაოდენობა; ფილტრის ცვლილებაზე ჯამი იცვლება.
- **AC-8** (US-6) Given ცხრილი ფილტრირებულია, When «Excel export», Then იქმნება `floors-report-YYYY-MM-DD.xlsx` 4 სათაურის ხაზით (სახელი, Email, ნომერი, შიდა), ხილული რიგებით, «სულ სართული» ხაზით; კონფლიქტიან უჯრას ⚠ აქვს.
- **AC-9** (US-7) Given ლისტში ჩანაწერი შეიცვალა, When «განახლება» ან გვერდის გადატვირთვა, Then ცხრილი ახალ მონაცემებს აჩვენებს ხელით ჩარევის გარეშე.
- **AC-10** (US-7) Given Bitrix მიუწვდომელია ან webhook არასწორია, When გვერდი იტვირთება, Then ჩანს წითელი ბანერი შეცდომის ტექსტით და «ხელახლა ცდა» ღილაკი, ცარიელი გვერდი არ რჩება.
- **AC-11** (US-7) Given გვერდი Vercel-ზეა და `BITRIX_WEBHOOK` არ არის დაყენებული, When გვერდი იტვირთება, Then ბანერში წერია ზუსტი ინსტრუქცია (Settings → Environment Variables → BITRIX_WEBHOOK → Redeploy).
- **AC-12** (უსაფრთხოება) Given რეპოზიტორია საჯაროა, When ვათვალიერებთ git ისტორიას, Then webhook URL/token არცერთ commit-ში არ არის; ჰოსტინგზე webhook მხოლოდ სერვერის ცვლადშია.

## Non-functional
- **წარმადობა**: სრული ჩატვირთვა (2 გვერდი ელემენტები + ველები + მომხმარებლები) ≈2 წმ; ≤500 ჩანაწერზე რენდერი შეუმჩნეველი. Bitrix REST ლიმიტი: 2 მოთხოვნა/წმ webhook-ზე, 20 მომხმარებელი ერთდროულად პრობლემა არ არის (თითო გახსნა 4–5 მოთხოვნა).
- **წვდომა**: Vercel-ის ბმული ღიაა (გადაწყვეტილება D-5). Proxy უშვებს მხოლოდ 3 read-only მეთოდს და აძალებს `IBLOCK_ID`.
- **აუდიტი**: არ არის (read-only).
- **ენა**: UI ქართულად; კოდი და ტექნიკური დოკუმენტაცია ინგლისურად.
- **მობილური**: ცხრილი ჰორიზონტალურად სქროლდება sticky სათაურით და პირველი სვეტით; სპეციალური მობილური განლაგება არ არის.
- **ბრაუზერები**: Chrome/Edge თანამედროვე ვერსიები (ES2020, `fetch`, CSS `position: sticky`).
